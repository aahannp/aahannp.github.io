Service-to-service workload identity · SDE-1

Shared secrets out. Tokens that expire in minutes in.

I worked on the S2S workload identity platform: the identity service that mints and signs tokens, the auth service exchange, a shared library for callers and receivers, and a reviewed repo of who may call whom. My parts: key compromise and revocation, the Kubernetes token verifier, bundle delivery to receivers, audit events and the staging rollout. It runs on staging with an end-to-end call passing. Scroll through the flow, or drive the demo yourself.

  1. Step 1 · Prove

    The workload shows its papers.

    It presents a Kubernetes projected service-account token: issued by the cluster, bound to the pod, never copied into a config file.

  2. Step 2 · Exchange

    Swap proof for a short-lived token.

    The auth service verifies that proof and the identity service mints a token that lives for minutes. Signing keys are KMS-wrapped and rotate automatically.

  3. Step 3 · Call

    Nothing long-lived on the wire.

    The caller sends the token with its request. If it leaks, it expires before it's worth much.

  4. Step 4 · Verify

    Check the signature, not a shared secret.

    The receiver checks signature, expiry and audience against the identity service's published key set (JWKS). Revoke a key and it leaves the set, so its tokens stop working everywhere.

  5. Step 5 · Decide

    Policy as code, fail closed.

    Grants live in a reviewed repo with CI validation. Receivers pull them as signed policy bundles, cache them, and keep the last good copy. If they can't verify, the answer is no.

  6. Step 6 · Roll out

    Shadow first. Kill switch always.

    Receivers start in shadow mode: evaluate policy, log what would have been denied, let the call through. Enforce comes once the would-deny count is flat. A central kill switch pushes receivers back to shadow from config, no redeploy, and a typo in the mode falls back to shadow, never to off or enforce. Identity checks never switch off.

      Audit pipeline · Intern

      Every token mint leaves a record. None of them slow a login.

      I built the audit mechanism in the identity service from scratch: an async event pipeline that records user deletions, workload principals, bindings, key compromises and every token mint, with metrics and unit tests.

      Writes happen off the request path into a bounded buffer, so a slow or unavailable audit store never adds latency to a login.

      The trade-off

      Async keeps a slow audit store from becoming a slow login. The price: an event still in memory can be lost if the process dies, so the buffer must be bounded and watched, never left to grow. Try "Slow audit store" in the demo.

        Password verification · Intern

        A login spike shouldn't take the service down with it.

        Password hashing is slow on purpose, which makes it the first thing to melt under load. Verification runs on a bounded worker pool: a fixed number of workers, a fixed-size queue, and an honest HTTP 429 the moment the queue is full. Push the load past capacity and watch what each setting costs.

        Reject early, not late.

        A 429 in a millisecond lets the client back off or retry elsewhere. A timeout after a long wait helps nobody and holds a connection the whole time.

        Don't do dead work.

        If the caller has already given up, hashing their password burns CPU for an answer nobody will read. The worker checks first and skips it.

        Size the queue from the timeout.

        Queue length × hash time ÷ workers has to stay under the caller's timeout. A bigger queue only hides overload until everything times out at once.

        Lazy hash migration

        Moving off bcrypt without a single reset email.

        You can't rehash a password you don't have, and the only time it legitimately exists is during a successful login. So the upgrade rides on login: verify against the stored bcrypt hash, answer the user, then rewrite the hash with Argon2id off the request path.

        Users never notice, and the old hashes drain out on their own. I designed and built this path in the auth service, backed by 1,000+ lines of tests.

        04How I think

        Six rules I keep relearning.

        Keep scrolling →

        1. 01

          Fail closed.

          If you can't verify who's calling or what they're allowed to do, the answer is no. An auth layer that fails open is decoration.

          WhereS2S receivers reject a bad signature or a revoked key in every mode, fall back to the last good signed policy, never to "allow", and a service doesn't report healthy until its receiver is ready.
        2. 02

          Shadow before enforce.

          Log what you would have denied before you deny it. The first real traffic always knows something your design doc doesn't.

          WhereS2S receivers ship in shadow mode and move to enforce once the "would deny" logs are clean.
        3. 03

          Bound every queue.

          An unbounded queue is a slow outage. Say no early, and never spend CPU on a caller who has already left.

          WhereThe password-verification pool: fixed workers, fixed queue, a fast 429, and dead work skipped.
        4. 04

          Always ship the off switch.

          Anything that can block traffic needs a way to stop blocking it without a deploy, and that switch should be boring to use.

          WhereThe S2S kill switch drops receivers back to shadow from config. In Relay, agent-to-agent messaging can be turned off in Settings.
        5. 05

          Audit what matters, off the hot path.

          If you can't answer "who did this, and when?" after an incident, you don't have security, you have hope.

          WhereThe identity service's audit pipeline: every token mint and key compromise, written async, expired by TTL.
        6. 06

          Boring tech, honest limits.

          Use the feature the platform already has, and write down what your design doesn't cover.

          WhereBounded queues and fail-fast limits instead of unbounded buffers. Relay's README names the risk it can't fix. This site: no framework, no build step.
